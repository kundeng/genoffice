# officebay — plan, 2026-09-13

Status: proposed, awaiting approval. Covers the work agreed in session on 2026-09-13, in dependency
order. Nothing here starts spec 02's slice selection; that waits until D and E are answered.

## Why this order

Three questions block everything downstream, and only one of them is a product decision:

1. **Can one agent see a project's sheet + slide + PDF at once and synthesize across them?**
   Unanswerable today by reading code — needs an instrumented build (A).
2. **Does officebay need to build a structural document layer, or route to one that exists?**
   `packages/pdf2docx` already produces `IrPage` — a tri-format IR that rebuilds to docx, pptx and
   xlsx. Needs measurement (B), not argument.
3. **What is officebay for, beyond a rebrand?** Owner decision (D), informed by 1 and 2.

The whitelabel work (C) is independent and mostly mechanical; it can run in parallel.

## A · Instrumentation: make the product observable end to end

**The problem.** Questions like "can a single AI see three documents in one project" currently get
answered by an agent reading source and narrating. That has been unreliable. The product must be
able to answer them by running.

**The seam already exists.** `AgentLoop` (`packages/agent-core/src/loop.ts:194`) accepts an `events`
option and emits `onToolStart`, `onToolExecuted` (with `snapshotBefore`), `onTurnEnd`, `onDone`,
`onError`. Every app constructs its loop with that option available
(`apps/docs/src/renderer/ai/AiPanel.tsx:626` and equivalents). Tracing therefore needs **no change to
app logic** — only an events implementation and a place to write.

### A1 · Trace recorder

A `TraceRecorder` implementing `AgentLoopEvents<T>`, writing JSONL: one record per turn, tool call,
tool result, error, and run completion, stamped with app, document path, and run id. Enabled by an
env var so ordinary runs are unaffected.

What it answers immediately: what tools the model actually called, in what order, with what inputs,
how many turns, where it failed, what it never tried.

### A2 · Headless scenario harness

Drive `AgentLoop` + one app's `AgentSkill` directly in Node with a scripted transport (canned model
responses) and assert the resulting tool sequence. No Electron, no UI, fast enough for CI.

Purpose: regression-test agent behavior itself — "given this prompt and this document, the agent
reads before writing, and the write is atomic."

### A3 · E2E probes on the real app

`e2e/` already launches the built shell with Playwright against a scratch `GENOFFICE_USER_DATA`
(`e2e/helpers.ts`), with video capture and 35 existing specs. Add probe specs that exercise the
questions we cannot answer statically, starting with the cross-document one:

> Create a project. Add a `.xlsx`, a `.pptx` and a `.pdf`. Open the AI panel. Ask for something that
> requires all three. Record the trace.

The trace from A1 shows exactly which documents the agent could see. If the answer is "only the
open one", that is a measured capability gap and the strongest possible input to spec 02.

**Deliverables:** `packages/agent-trace` (or `tools/`), a harness, at least three probe specs, and a
findings note in `docs/research/`.

## B · Measure the real ingestion path

**Correction to record.** The 2026-09-13 math probe measured `pdf.js getTextContent` — the PDF
_viewer's_ text layer — and concluded structure is absent. That conclusion holds for that path only.
`packages/pdf2docx` runs a different pipeline: PDFium glyph extraction → its own layout analysis
(paragraph breaks by gap/indent/short-line/font-step, multi-column gutter solving, lattice and
stream table detection, header/footer peeling, hyphenation, lists, footnotes) → `IrPage`.

**B1.** Run `extractIrDocument()` on the same chapter-2 pages and compare block structure against the
text-layer result. Update `tools/probe-math-extraction.mjs` to report both paths side by side, and
correct pillar P4 against whichever result holds.

**B2.** Assess `IrPage` as officebay's L1 candidate. It already carries typed blocks in reading
order, per-page quality (`status: ok | degraded | scanned | ocr`, `confidence`), and rebuilds to
three formats. What it does **not** carry is stable identity — no ids to anchor a mark to and
resolve after an edit. Record precisely what must be added rather than what must be built.

**Deliverable:** one research note answering "build or inherit" for the structural layer, with
numbers.

## D · Product definition (owner decision)

The question this plan cannot answer from code: **what advancement does officebay offer avid
learners and knowledge workers that the inherited product does not**, and what would people pay for.

The evidence now available to inform it:

- **The suite already reads deeply.** `pdf2docx` reconstructs document structure from glyphs, in
  five scripts, to a tri-format IR. That is a genuine asset, currently used only for file conversion.
- **The agent is per-document.** One `AgentLoop`, six `AgentSkill` adapters, each bound to one open
  document. No cross-document context surface exists (A3 will confirm or refute).
- **Marks exist; anchoring does not.** Highlights, notes and ink ship. `IrPage` has no stable ids,
  so nothing can point at a block and still find it after an edit.

That gap — **structure without identity, agents without a corpus** — is where a differentiated
product plausibly sits: a reader whose marks become durable, resolvable anchors, and an agent that
can work across a project rather than one file. Whether that is the product, and which parts are
free versus paid (individual, and later community), is the decision to make.

Fork evidence worth borrowing regardless of direction: airy's headless MCP server exposing the
document engines to coding agents (8,481 LOC, and a shape officebay may want rather than rebuild),
and WisWork's write-safety sequence (propose → confirm → one atomic write → verify by fingerprint →
restore on mismatch, with "uncertain" as a distinct outcome from "failed").

## E · Developer-facing architecture documentation

The existing `2026-09-13-codebase-walk.md` gets a new developer running. The existing
`2026-09-13-component-decomposition.md` is an inventory, which is not understanding. Both need to be
replaced by one document that explains **how the system actually works**:

- one `AgentLoop` in `packages/agent-core`, generic over snapshot type, owning history, compaction,
  cancellation and rollback;
- six `AgentSkill` implementations — `{ systemPrompt, tools, buildContext, executeTool }` — one per
  editor, each speaking its own editing vocabulary;
- why there is no shared document model: a slide is a canvas, a spreadsheet is a formula graph, a
  PDF page is immutable, and any common denominator would be a lie each adapter then works around;
- the commit discipline every app converges on: read state → build a batch → validate the whole
  batch → apply atomically as one undo step → verify → roll back on failure;
- worked example: slides' `execute_slide_script`, where the model writes JS evaluated against real
  geometry in a sandboxed interpreter, collects primitives rather than mutating, ships them as one
  IPC transaction, and receives a layout audit to self-correct from;
- the ingestion pipeline: PDFium glyphs → spans → lines → blocks → `IrPage` → docx/pptx/xlsx.

Written per house-rules §6: entry points named, ASCII diagrams at process and trust boundaries, real
code for the decisions that carry the design, one numbered trace, and stated limits.
